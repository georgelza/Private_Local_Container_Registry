# 9. Registry TLS and vcluster image pull

How the local self-signed registry certificate is created, served, trusted and
consumed — and the single string that must agree in five places.

Scope: `deploy/` only. The registry is the sole image source for vcluster pods,
so every core service deployment depends on this mechanism working. Kafka,
Postgres and Vault are not involved.

Evidence convention used throughout:

- **[measured]** — observed by running the code, with the output shown
- **[read]** — inferred by reading the code

Line references are to files in this directory.

---

## 1. The mechanism in one picture

A vcluster node is a Docker container running k3s. The kubelet inside it must
fetch an image from a registry that is *another* Docker container on the *same*
Docker network, over HTTPS, using a certificate nothing else has ever heard of.
Four mechanisms cooperate.

```
                        ┌──────────────────────────────────────────┐
                        │  HOST  (macOS, Docker Desktop)            │
                        │                                          │
   ①  make certs        │   openssl                                │
      ────────────►     │     ca.key ──signs──► ca.crt  (CA, 730d) │
                        │                  │                     │
                        │                  └──signs──► server.crt │
                        │                              (leaf, 2d) │
                        │                                          │
   ②  registry serves   │   ┌──────────────────────────────┐      │
      ────────────►     │   │ core-registry  (registry:2)  │      │
                        │   │  :5000  TLS                  │      │
                        │   │  /certs/server.crt  (ro)     │◄─────┼──┐
                        │   │  /certs/server.key  (ro)     │◄─────┼──┤
                        │   └───────────────┬──────────────┘      │  │
                        │                   │                     │  │
   ③  CA into containerd│   ┌───────────────▼──────────────┐      │  │
      ────────────►     │   │ vcluster node container       │      │  │
                        │   │                              │      │  │
                        │   │  /etc/containerd/certs.d/    │      │  │
                        │   │    host.docker.internal:5001/ │      │  │
                        │   │      ca.crt        ◄─────────┼──────┘  │
                        │   │      hosts.toml    ◄── (75-byte file)  │
                        │   │                              │     │
                        │   │  config.toml:                │     │
                        │   │    config_path =             │     │
                        │   │      "/etc/containerd/certs.d"     │
                        │   │                              │     │
                        │   │  containerd  ◄── SIGHUP ─────┼─────┘
                        │   │    killed; systemd restarts  │
                        │   │    it ~7s later, new PID    │
                        │   └───────────────┬──────────────┘
                        └───────────────────┼──────────────────
                                            │
   ④  kubelet pulls  ◄─────────────────────┘
      ─────────────►
        HTTPS GET https://host.docker.internal:5001/v2/…
        cert presented ──► verified against certs.d/…/ca.crt
```

Chain of custody:

| # | step | where | artefact |
|---|---|---|---|
| ① | `make certs` | `Makefile` 1123–1159 | `ca.crt` + `server.crt` in `data/registry/certs/` |
| ② | compose mounts `certs/` into the registry | `docker-compose.yml` | serves HTTPS on `:5000` |
| ③ | `k8s` target step `[2/10]` | `Makefile` 324–335 | containerd trust store in each node |
| ④ | the kubelet pulls | node | a running container |

**The structural weakness:** ① and ③ live in different files, in different
Makefile targets, and nothing validates that they agree. Step ③ can complete
fully — every file copied, `✓ <node> patched` printed — while producing a node
that cannot pull. §2 is the most common way that happens.

## 2. The authority contract

**One string, `host.docker.internal:5001`, appears in five places.** Three
different files, no validation.

```
                    host.docker.internal:5001
                    ═══════════════════════════════
   ┌────────────────┬───────────────────┬─────────────────┬────────────────┐
   ▼                ▼                   ▼                 ▼                ▼
[1] SAN         [2] certs.d         [3] hosts.toml    [4] ca_file      [5] image
DNS.3 in       directory name      server =         path inside     reference in
san.cnf       under certs.d/       "https://…:5001" hosts.toml     the manifest
               │                                     │                │
  Makefile     Makefile             scripts/         scripts/        k8s/core1/
  `certs`      (cp target path)     containerd-      containerd-     4.*.yaml
                                    hosts.toml       hosts.toml
```

If these disagree, the CA can be present, correct, and **never consulted**. No
error, no warning, no log line.

### Why the gateway name, not `localhost`

```
  ┌─ your Mac ────────────────────────────────────────────────┐
  │   host process → https://localhost:5001   (published port)│
  │                                                          │
  │   ┌─ Docker Desktop VM ─────────────────────────────────┐ │
  │   │  vcluster node container                           │ │
  │   │    "localhost" here = THIS CONTAINER               │ │
  │   │    no registry on :5001 inside it                  │ │
  │   │                                                   │ │
  │   │    host.docker.internal ──► VM gateway ──► host    │ │
  │   │                          ──► published port 5001   │ │
  │   └───────────────────────────────────────────────────┘ │
  └──────────────────────────────────────────────────────────┘

  host-side tools → localhost:5001
  kubelet in a node → host.docker.internal:5001
```

`host.docker.internal` is Docker's embedded DNS name for the VM gateway. It
resolves to the host from inside any container, and the host's published port is
then reachable.

### Symptom table

| if this is wrong | symptom |
|---|---|
| [1] SAN missing the name | `x509: certificate is valid for localhost, not host.docker.internal` |
| [2] certs.d directory named `localhost:5001` | `x509: certificate signed by unknown authority` — **the CA is right there and unread** |
| [3] `hosts.toml` missing | identical to [2] |
| [4] `ca_file` path wrong | identical to [2] |
| [5] manifest says `localhost:5001` | `manifest unknown` — the node asked *itself* |
| [5] manifest has an `https://` prefix | manifest rejected; a scheme is invalid in an image reference |

**Cases [2], [3] and [4] are the dangerous family**, because the node still
*looks* correctly patched:

```
  ca.crt      present   ✔
  hosts.toml  present   ✔
  config_path set       ✔
  → "✓ node patched"
  → every pull still fails with "certificate signed by unknown authority"
```

`✓` is printed unconditionally: every command in the loop is individually guarded
with `2>/dev/null || true` and nothing afterwards checks the result. The only way
to know is to read the state back:

```bash
docker exec <node> ls -la /etc/containerd/certs.d/host.docker.internal:5001/
docker exec <node> cat    /etc/containerd/certs.d/host.docker.internal:5001/hosts.toml
docker exec <node> grep    config_path /etc/containerd/config.toml
```

## 3. Certificate creation — `make certs`

`Makefile` 1123–1159, the `certs` target (ADR-56). Six make prerequisites, each
one `openssl`. Runs automatically as part of `make run`.

```
   ca.key                      RSA 4096, private, chmod 0600
      │  openssl req -x509 -new -nodes -key $(CA_KEY) -sha256 -days 730
      │         -subj "/CN=CORE Local Registry CA"
      ▼
   ca.crt ───────────────────► self-signed ROOT      validity 730 days
      │                      (generated once, reused)
      │  openssl x509 -req -in $(SERVER_CSR) -CA $(CA_CRT) -CAkey $(CA_KEY)
      │         -CAcreateserial -out $(SERVER_CRT) -days 2 -sha256
      │         -extensions v3_req -extfile $(SAN_CONFIG)
      ▼
   server.crt ───────────────► LEAF, signed by the CA   validity 2 days
      │                      (re-minted on every `make run`)
      └─► SANs, from data/registry/certs/san.cnf:
            DNS.1 = localhost                 ← host-side tools
            DNS.2 = core-registry             ← in-network clients (the UI)
            DNS.3 = host.docker.internal       ← THE KUBELET  ★
            IP.1  = 127.0.0.1                 ← IP-literal clients
```

**Design intent:** the leaf is deliberately short-lived (2 days) and replaced on
every stack bring-up, so a leaked trust anchor is near-worthless. The
consequence is that the CA private key becomes load-bearing state — see §9 D7.

### What each SAN is for

A TLS client checks **the name it dialled** against the SAN list. It does not
check the server's own hostname. So one entry per client vantage point:

| SAN | who dials it | verifies? |
|---|---|---|
| `DNS.1 localhost` | host-side tools: `curl --cacert … https://localhost:5001` | yes |
| `DNS.2 core-registry` | the UI's nginx, via `NGINX_PROXY_PASS_URL` | **no** — `NGINX_PROXY_SSL_VERIFY: "off"` |
| `DNS.3 host.docker.internal` | **the vcluster kubelet** | yes ★ |
| `IP.1 127.0.0.1` | IP-literal clients | yes |

**[measured]** against a certificate carrying `DNS:localhost, DNS:core-registry,
DNS:host.docker.internal`, CA trusted by the client:

```
  name the CLIENT dials        verdict
  ──────────────────────────   ──────────────────────────────────
  localhost                    ✅ accepted
  core-registry                ✅ accepted
  wrong.example                ❌ Hostname mismatch
```

`DNS.2` is **not load-bearing** — the UI does not verify its upstream. It is
there for accuracy. `DNS.3` is the one that matters.

## 4. Serving — `docker-compose.yml`, `core_registry`

```yaml
  core_registry:
    image: registry:2
    container_name: core-registry
    ports:
      - ${HOST_PORT_REGISTRY:-5001}:5000      # host :5001 → container :5000
    volumes:
      - ./data/registry:/var/lib/registry     # blobs
      - ./data/registry/certs:/certs:ro       # TLS material, read-only
    environment:
      REGISTRY_STORAGE_DELETE_ENABLED: "true"
      REGISTRY_HTTP_TLS_CERTIFICATE: /certs/server.crt
      REGISTRY_HTTP_TLS_KEY:       /certs/server.key
```

- The container serves on **`:5000`**; the host publishes **`:5001`**. Every URL
  in tooling is `…:5001` because that is the host's published port.
- **The CA is never given to the registry.** It is given only to the *clients*.
  The registry presents the leaf and lets each client decide.
- `data/registry/certs/` sits in the **same directory as the blobs**, which is
  why `scripts/purge_registry.sh --full` preserves `certs/` and why
  `make down` destroying `data/registry` destroys the CA key (D7).

### Healthcheck

```yaml
    healthcheck:
      test: ["CMD-SHELL", "wget --no-check-certificate -q -O /dev/null https://localhost:5000/v2/_catalog || exit 1"]
```

`wget`, not `curl`: `registry:2` is BusyBox-based and has **no `curl`**:

```
$ docker run --rm --entrypoint sh registry:2 -c 'command -v curl'   # no output, exit 1
$ docker run --rm --entrypoint sh registry:2 -c 'command -v wget'   # /usr/bin/wget
```

`--no-check-certificate` is required because the registry serves HTTPS with our
own self-signed CA.

## 5. Injection — `k8s` target step `[2/10]`

`Makefile` 324–335. **Inline in the make recipe, not a script.** There is no
`scripts/patch_registry_ca.sh`; the only script that touches a node's `certs.d`
is `recover_registry_ca.sh`, which copies the CA *out* of a node for recovery.

```make
@for node in vcluster.cp.$(VCLUSTER) vcluster.node.$(VCLUSTER).worker-1 \
           vcluster.node.$(VCLUSTER).worker-2 vcluster.node.$(VCLUSTER).worker-3; do \
  if docker ps --format '{{.Names}}' | grep -q "^$$node$$"; then \
    docker exec $$node mkdir -p /etc/containerd/certs.d/host.docker.internal:5001 ; \
    docker cp ./data/registry/certs/ca.crt  $$node:.../ca.crt      ; \
    docker cp ./scripts/containerd-hosts.toml $$node:.../hosts.toml ; \
    docker exec $$node sh -c 'sed -i "s|config_path = \"\"|config_path = \
                                \"/etc/containerd/certs.d\"|" /etc/containerd/config.toml' ; \
    docker exec $$node pkill -HUP containerd ; \
    echo "  ✓ $$node patched"; \
  else \
    echo "  ⚠ $$node not running (skipped)"; \
  fi; \
done
```

### Before and after

```
  BEFORE (as the vcluster node image ships)      AFTER
  ────────────────────────────────              ─────────────────────────────
  config_path = ""            ← certs.d        /etc/containerd/certs.d/
                               is IGNORED         host.docker.internal:5001/
  no certs.d directory                            ca.crt        ← anchor
  no hosts.toml                                   hosts.toml    ← instruction
                                                 config_path = "/etc/containerd/certs.d"
```

**`config_path` is the step most often forgotten.** containerd 2.x reads
host-level CA config from the directory named by `config_path` and ignores
`certs.d/` entirely while it is empty. The node image ships `config_path = ""`.
A correctly named CA can sit on disk, unread, indefinitely.

### `scripts/containerd-hosts.toml`

75 bytes, **no trailing newline**. Verbatim:

```toml
server = "https://host.docker.internal:5001"

[host."https://host.docker.internal:5001"]
  capabilities = ["pull", "resolve"]
  ca_file = "/etc/containerd/certs.d/host.docker.internal:5001/ca.crt"
  skip_verify = true
```

- `server` — the authority, with scheme
- `ca_file` — absolute path, **as seen from inside the node**
- `capabilities` — minimum for an image source; without `resolve`, tag
  resolution can return empty on newer containerd
- `skip_verify = true` — **see D4.** Contradicts the `ca_file` directly above it

> **`hosts.toml` is what makes `ca.crt` mean anything.** Without it the CA is an
> inert file nobody reads. This is the single most fragile dependency in the
> mechanism, because the file is tiny and the copy is failure-guarded.

### The reload is a kill, not a reload

**[measured]** running only that line against a live node:

```
  before      pid=1260   systemd=active
  pkill -HUP containerd
  t+ 2s       pid=-      systemd=activating
  t+ 4s       pid=-      systemd=activating
  t+ 6s       pid=-      systemd=activating
  t+ 8s       pid=2174   systemd=active      ← different PID
```

SIGHUP does not reload containerd — it terminates it. The new config takes effect
only because systemd starts a *new* process (note the PID change), ~7 s later.
**During that window the node has no container runtime** and every pod on it is
stuck. The loop prints `✓ <node> patched` before any of this.

`systemctl restart containerd` is survivable; SIGHUP is a kill.

### Why patching must be part of creation

The CA is delivered with `docker cp` into a running container's filesystem. It is
**not** in the node image and **not** on any volume. Therefore:

| event | CA survives? |
|---|---|
| node keeps running | yes |
| worker rescheduled after a crash | **no** |
| `vcluster delete` + `create` | **no** |
| node added later (scale-up) | **no** |

A rescheduled worker comes up looking healthy and cannot pull anything. This is
why `make k8s` always re-patches rather than checking whether it already ran.

## 6. Consumption — the kubelet pull

```yaml
image: host.docker.internal:5001/core-users:0.6
imagePullPolicy: Always
```

```
  kubelet (in node)
    │  needs host.docker.internal:5001/core-users:0.6, does not have it
    ▼
  CRI → containerd  (v2.2.3)
    │  config.toml → config_path = /etc/containerd/certs.d
    │  scans for a subdirectory matching the authority it is dialling
    │  finds  host.docker.internal:5001/hosts.toml
    │  reads  server, ca_file, skip_verify
    ▼
  HTTPS GET https://host.docker.internal:5001/v2/core-users/manifests/0.6
    │  TCP → VM gateway :5001
    │  TLS handshake; registry presents server.crt
    │  chain vs ca.crt            (condition a)
    │  hostname vs the SANs       (condition b)  ★
    ▼
  manifest + layers → unpacked → container started
```

**Two conditions must hold:**

| | condition | established by | if it fails |
|---|---|---|---|
| **(a)** | the CA that signed the leaf is in the store containerd consults | `hosts.toml` + `ca.crt` + `config_path` (step `[2/10]`) | `x509: certificate signed by unknown authority` |
| **(b)** | the dialled name is in the certificate's SANs | `DNS.3 = host.docker.internal` in `certs` | `x509: certificate is valid for localhost, not host.docker.internal` |

**Because `skip_verify = true`, (a) is not enforced at runtime.** A successful
pull proves (b) and connectivity — it does **not** prove the CA is correct. A
green deploy is not, by itself, evidence that this mechanism works.

### Why `imagePullPolicy: Always` is load-bearing

Default is `IfNotPresent`. After any earlier successful pull the image is already
in the node's containerd, so `IfNotPresent` serves from local cache, **the
registry is never contacted, the CA is never exercised, and the pod still starts
green.** A pull test using the default policy can pass with the trust chain
completely broken.

## 7. The second trust store — the docker daemon

Two independent stores. The repo handles one.

| | who needs it | when | handled? |
|---|---|---|---|
| **containerd** in each node | the kubelet | pull | **yes** — step `[2/10]` |
| **docker daemon** on the host | `docker push` / `docker pull` | build | **no** |

`curl` honours `--cacert`, so every `curl` preflight in the repo passes. The
docker daemon has its own store and ignores `--cacert`, so `docker push` needs it
populated. Nothing in the repo does that. Manual prerequisite:

```bash
# Docker Desktop on macOS reads the USER-level path.
# /etc/docker/certs.d is the Linux path and is silently ignored on macOS.
mkdir -p ~/.docker/certs.d/localhost:5001
cp data/registry/certs/ca.crt ~/.docker/certs.d/localhost:5001/ca.crt
# restart Docker Desktop
```

The deferral is explicit — `scripts/deploy-app.sh:104`:

```bash
# Use -k for preflight (self-signed cert); CA cert verification happens at build/push time
if curl -kfsS "https://${reg_host}:${reg_port}/v2/_catalog" ...
```

`core/build/Makefile:118` then honours it with `curl --cacert` — before running
`docker buildx build --push`, which goes through the daemon. The preflight proves
the CA one way; the push needs it known another way. The deferral lands in the gap.

## 8. Diagnosing a failed pull

```
  symptom                                        → condition failed
  ─────────────────────────────────────────────────────────────────────
  x509: certificate signed by
    unknown authority                                (a) CA not trusted
                                                     ↳ §5: ca.crt in the node?
                                                       hosts.toml there?
                                                       config_path set?
                                                       or is the CA STALE (D7)?
  x509: certificate is valid for
    localhost, not host.docker.internal              (b) SAN missing
  x509: certificate has expired                       2-day leaf expired
  lookup host.docker.internal: no such host          DNS, not TLS
  connection refused                                 registry not listening
  manifest unknown / 404                             tag not in the registry
  manifest rejected by the API server                scheme in the image ref,
                                                     or a misplaced field
```

```bash
# is the CA on disk the CA the registry is SERVING?
curl -fsS --cacert data/registry/certs/ca.crt https://localhost:5001/v2/_catalog
curl -fsSk                             https://localhost:5001/v2/_catalog   # -k: reachable at all?

# per node, by hand
docker exec <node> ls -la /etc/containerd/certs.d/host.docker.internal:5001/
docker exec <node> cat    /etc/containerd/certs.d/host.docker.internal:5001/hosts.toml
docker exec <node> grep    config_path /etc/containerd/config.toml
docker exec <node> sh -c 'systemctl is-active containerd'
docker exec <node> journalctl -u containerd --no-pager -n 20
```

The first pair distinguishes **"registry is down"** from **"registry is serving
a different certificate than the one on disk"** — different root causes, and from
a pull failure they are indistinguishable. The second is caused by re-minting
certs while the registry was running (D7), and its only symptom is
`unknown authority`, which reads like a CA problem.

## 9. Defects

**[D1] Healthcheck could never pass — fixed.** It used `curl`, which
`registry:2` does not have, so the container was permanently `unhealthy`. Masked
because the UI used `condition: service_started`. Now `wget`. The latent risk
that remains: `condition: service_healthy` is the *correct* dependency — the
UI's NGINX proxy resolves its upstream once at startup and fails permanently
against a registry that is created-but-not-listening — and with a real
healthcheck that switch is finally safe.

**[D2] `pkill -HUP containerd` is a kill, not a reload.** §5. Terminates the
runtime; systemd restarts it ~7 s later. Every node has no runtime for that
window, every pod is stuck, and the loop has already printed `✓`. Described as a
reload in both the code comment and `README.md`.

**[D3] The loop cannot fail.** All five steps individually guarded with
`2>/dev/null || true`; `✓ <node> patched` echoed unconditionally. A missing
`hosts.toml`, a wrong certs.d directory name, or a `config_path` that never took
all produce the same output as success. With §2, this is what makes that failure
family invisible.

**[D4] `skip_verify = true` means the CA is never verified.** It contradicts
`ca_file` directly above it. A pull succeeds even if `ca.crt` is the wrong CA or
is stale — so the failure this mechanism exists to prevent is undetectable from
the pull result.

**[D5] `vault-keys` Secret is in the wrong namespace.** `make vault-secret`
creates it `-n core`; every core service Deployment lives in `admin` and mounts
`secretName: vault-keys`. Secrets are namespace-scoped, so the mount can never
resolve and pods hang in `ContainerCreating`:

```
Warning  FailedMount  MountVolume.SetUp failed for volume "vault-keys" :
                       secret "vault-keys" not found
```

Not in the registry path, but it blocks every core service.

**[D6] `README.md` §"vcluster Node Trust Patch" documents a different mechanism
than the code implements:**

| `README.md` says | code does |
|---|---|
| nodes are `worker-1, worker-2, worker-3` | `vcluster.cp.<name>`, `vcluster.node.<name>.worker-{1,2,3}` |
| certs.d path is **`localhost:5001`** | **`host.docker.internal:5001`** |
| no `hosts.toml` copied | copies it |
| no `config_path` set | sets it |
| "SIGHUP reloads containerd without restarting the node" | it kills it (D2) |
| "Idempotent: safe to re-run on every `make k8s`" | each run kills containerd again |
| healthcheck `curl -kfsS …` | `wget …` (D1) |
| manifests use `image: https://host.docker.internal:5001/…:0.1` | `host.docker.internal:5001/…:0.6` — 0 with a scheme across all four cores |

The `localhost` vs `host.docker.internal` row is the dangerous one: it teaches
case **[2]** from §2 — a correct CA in a directory containerd never reads, with a
green tick printed. The `https://` row would have anyone following it write
manifests the API server rejects.

**[D7] `make down` destroys the CA private key while nodes keep the old CA.**
`make down` does `rm -rf ./data/registry`, which contains `certs/ca.key`. That
key exists nowhere else; nodes hold only the public `ca.crt`. After
`make down` + `make run`:

- the registry serves a certificate from a **brand-new** CA, and
- every running node still trusts the **old** CA.

Nothing in `make run` re-patches the nodes — only `make k8s` step 2 does, and it
is not part of `make run`. Result: a stack that reports healthy, and a cluster
where every pull fails with `unknown authority` — which reads like a CA problem
rather than a lifecycle-coupling one. `scripts/recover_registry_ca.sh` exists
precisely to copy the CA back out of a node and documents that `ca.key` is
unrecoverable: a workaround for an ordering defect, not a fix.

**[D8] The docker daemon's trust store is never populated.** §7.

## 10. Recommended changes

In priority order.

1. **Rewrite `README.md`'s registry section from the Makefile and delete the
   stale snippets** (D6). It currently teaches a certs.d path that cannot work,
   and the code's own output is unfalsifiable (D3).

2. **Extract `scripts/patch_registry_ca.sh` and call it from the Makefile.** The
   mechanism most worth testing is the part with no seam. A script is the
   precondition for testing it.

3. **Make that script verify, then exit non-zero.** Read `ca.crt`, `hosts.toml`
   and `config_path` back out of each node, and assert the certs.d directory
   name matches the authority the manifests use. That one check closes D3 and
   the whole §2 family.

4. **Add `make registry-daemon-ca`** to populate the docker daemon's trust store,
   so the push path stops depending on manual setup (D8).

5. **Replace `pkill -HUP containerd` with `systemctl restart containerd`**, and
   correct the comments describing it as a reload (D2). **[measured]** the
   restart is survivable, the SIGHUP is not. Then wait for
   `systemctl is-active containerd` before printing `✓`.

6. **Decide what `skip_verify` should be** (D4). Either set it `false` and accept
   that a stale CA fails loudly — the correct choice, and it makes `preflight`
   and the pull agree — or keep `true` and document explicitly that the CA is
   best-effort and `preflight` is the only check. What is not defensible is
   shipping `ca_file` and `skip_verify = true` in one file with nothing

7. **Derive the authority once.** Five occurrences of
   `host.docker.internal:5001` across three files with no validation. A single
   `REGISTRY_AUTHORITY` feeding the SAN list, the certs.d path, `hosts.toml` and

8. **Move `make vault-secret` to the namespaces that consume it** (D5), or create

9. **Stop `rm -rf ./data/registry` in `make down`** (D7) — or preserve
   `certs/ca.key` and wipe only the leaf. `scripts/purge_registry.sh --full`

10. **Reconsider the 2-day leaf, or re-patch nodes from `make run`.** Either
